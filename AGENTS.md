# AGENTS

## Purpose

This file is for future maintainers and coding agents working in this repository.

## Working Assumption

The active product is the `sing-box` based portable managed browser package, not the older Xray launchers.

The repository may later host both Windows and macOS implementations, but Windows is the only active platform unless the task explicitly targets macOS work.

Primary source projects:

- `AgentBrowserUi/`
- `SingBoxStart/`
- `SingBoxStop/`
- `libs/`

Future platform-specific source should live under:

- `platforms/<platform>/`

Legacy projects:

- root `Program.cs` and `Launcher.csproj`
- `ChromiumLauncher/`
- `StopXray/`

Do not treat legacy projects as the default target unless the task explicitly asks for Xray or historical rollback.

## Edit Strategy

- edit source projects first
- rebuild binaries second
- copy fresh outputs into `AgentBrowser_Windows/` last
- avoid editing packaged binaries or generated files directly except for package metadata like `README.txt` or `ui-settings.json`

## Runtime Facts

- `Start.exe` and `Stop.exe` require administrator rights
- `AgentBrowserUI.exe` does not own the tunnel lifecycle directly
- `core/config.json` is generated by the UI
- `core/sing-box.log` is the primary network runtime log
- browser auth state is not guaranteed to survive transfer to another Windows machine

## Debug Order

When something “does nothing”, check logs in this order:

1. `ui.log`
2. `start.log`
3. `stop.log`
4. `core/sing-box.log`

## Common Failure Modes

- UI launches but helper exe is blocked or missing
- `sing-box check` passes but the tunnel still cannot connect
- `VLESS` is syntactically valid but fails at DNS bootstrap or remote handshake
- browser processes survive shutdown because Windows process inspection is transient
- copied browser profiles appear intact but auth is lost because protected browser secrets cannot be decrypted on the new machine

## Build Notes

Use `dotnet publish` with `-r win-x64 --self-contained true` for all active projects.

Preferred commands:

```bash
dotnet publish AgentBrowserUi/AgentBrowserUi.csproj -c Release -r win-x64 --self-contained true
dotnet publish SingBoxStart/Start.csproj -c Release -r win-x64 --self-contained true
dotnet publish SingBoxStop/Stop.csproj -c Release -r win-x64 --self-contained true
```

## Packaging Notes

When refreshing the Windows package:

- copy the rebuilt `AgentBrowserUI.exe` and required runtime DLLs
- copy rebuilt `Start.exe`
- copy rebuilt `Stop.exe`
- keep `core/`, `App/`, `Data/`, `Other/`, and `Profile/` intact unless the task explicitly changes packaged runtime contents

## Repository Hygiene

- use `AgentBrowser.sln` as the default entry point for active development
- treat the git repository as source, docs, and build-governance only
- do not commit packaged runtime binaries from `AgentBrowser_Windows/`
- do not commit `AgentBrowser_Windows.zip`
- do not commit downloaded vendor bundles from `resurs/`
- do not commit local `bin/`, `obj/`, logs, or support bundles
- if operator-ready binaries must be shared, use release artifacts or external storage instead of normal git history

## Documentation Rule

If architecture changes again, update at minimum:

- `DECISION_LOG.md`
- relevant `ADR/*.md` entry if the change is a durable decision
- `SOURCES_OF_TRUTH.md`
- `DOCUMENT_REGISTRY.md`
- `README.md`
- `ARCHITECTURE.md`
- `STATUS.md`
- `DEVLOG.md`

## DevLog Discipline

After every source or package-facing change, append an entry to `DEVLOG.md`.

Each new entry must include:

- local date and time of the change
- reason for the change
- files that were edited
- package or runtime notes if binaries or zip artifacts were refreshed

## Documentation Governance

When docs disagree:

1. use `SOURCES_OF_TRUTH.md` to resolve domain ownership
2. use `DOCUMENT_REGISTRY.md` to confirm the document is official and active
3. if the change is a durable decision, update `DECISION_LOG.md` and the relevant ADR
4. update the stale document in the same change when feasible

## ADR Trigger Rule

Create a new ADR when the change modifies a durable decision, including:

- product positioning
- active runtime architecture
- security or process-ownership boundary
- workspace or packaging model
- operator/admin UX model
- documentation governance model

Do not create a new ADR for routine fixes, logging changes, packaging refreshes, or implementation-only refactors that preserve the same decision.

Use `ADR/ADR-TEMPLATE.md` when creating a new ADR.

## Completion Gate

Do not treat a non-trivial change as complete until:

1. `CHANGE_CHECKLIST.md` has been satisfied
2. `DEVLOG.md` has the matching entry
3. the final response states what was changed and what was not verified

If package artifacts or release candidates changed, also review `RELEASE_CHECKLIST.md` before calling the work complete.

## Product Guardrail

Do not evolve the docs or product messaging toward “anti-detect”, “undetectable”, or stealth claims by default.

Prefer:

- managed browser
- isolated profile browser
- session-controlled browser runtime
